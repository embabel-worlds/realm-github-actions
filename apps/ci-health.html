How it works

Every number on this page is the result of a saved view on the world, run by name with the parameters you set. This page renders rows; the view's Cypher is what runs.

1. The data

All of it comes from realm-github-actions, reading the GitHub REST API with a token that can read Actions on the repository. Nothing is mirrored: a view pins the repository by name, the engine fetches from GitHub for that query, materialises transient nodes, runs the Cypher, and rolls them back.

(ActionsWatch {full_name, branch})        the watchlist — the one STORED type; the picker and the fleet read it
   -[:HAS_RUN_HISTORY]->   (WorkflowRun)    the same cached history, off every followed repository at once

(GitHubRepository {full_name})            the door — pinned by 'owner/repo'; the same label realm-github anchors issues on
   -[:HAS_WORKFLOW]->      (Workflow)       GET /repos/{o}/{r}/actions/workflows                        cached 1 h
   -[:HAS_WORKFLOW_RUN]->  (WorkflowRun)    LIVE: GET .../actions/runs?created=>=since, newest first    cached 5 min
   -[:HAS_RUN_HISTORY]->   (WorkflowRun)    HISTORY: one GET per 100 runs per calendar month, this month and last   closed month cached 400 days, current month 30 min
         -[:HAS_JOB]->            (WorkflowJob)     GET .../runs/{id}/jobs?filter=all, one call per run   cached 5 min
               -[:HAS_ANNOTATION]->  (CheckAnnotation) GET .../check-runs/{job}/annotations, one call per job   cached 1 h
  • Two doors to the same runs. Completed runs never change, so every panel here — the fleet, overview, runs, failures, flaky, reading, and a run's jobs — reads history: this month and last as calendar periods (at least the last 31 days), one GitHub page per hundred runs, a closed month cached for 400 days and the current month for 30 minutes. The first read of a repository costs about a dozen calls (five to ten seconds); every later read of any window costs nothing until the current month's slice expires. Only ActionsRecentRuns reads the live door, with the window pushed down to GitHub's created filter. The views keep every filter and limit on projected variables and on a WITH, not on the fetch, which is what lets all of them share one cached read per repository.
  • Per user, and warmed once. The world keeps that cache per signed-in user, and two panels missing it at the same moment would each sweep GitHub. So this page reads one small view per followed repository first, one at a time, and opens the panels only when the repository is warm. The first read of a repository in a session takes five to ten seconds and says so; after that, panels answer in well under a second.
  • Freshness. The current month's slice is re-read after 30 minutes; a closed month after 400 days. A run's jobs are re-read after six hours, annotations after a day, workflows after six hours. A figure that disagrees with GitHub inside those windows is the cache, not a bug; the engine reports when each producer was actually read. Known edge: a run still in progress when its month closed, or re-run in a later month, keeps in history the state it had when that month was last read.
  • The fleet. "Broken mains" is, per followed repository and workflow, the latest completed run on the watched branch; "broken PRs" is, per pull-request branch, the latest completed run. Both sweep every followed repository in one query through the watchlist's door.
  • Run time is updated_at − run_started_at on a completed run; queue time is run_started_at − created_at. Values arrive from GitHub as strings; the views coerce.
  • The daily watch (ciWatch in the realm's handlers) runs at 08:00 on weekdays once an operator adopts it, over the repositories seeded as ActionsWatch. It is not what this page reads.

3. When it looks wrong

  • Failed runs, failing steps, causes are empty: no run in the window concluded failure. Green, not broken.
  • Flaky is empty: nothing was re-run to success in the last 30 days, so no job could both fail and pass.
  • A red notice is the lookup failing: a token without access, a repository that does not exist, GitHub unreachable. It is never shown as a zero.
  • Partial answer: the engine hit the page cap and GitHub had more. Choose a dated window and the fetch is scoped at the source.
  • An answer to a question that has different figures from a tile: the question was composed by the generator with its own window ("this week" may mean since Monday). Open what ran under the answer and compare the WHERE clause; ask with "in the last 7 days" to get the view's own window.
  • A run's jobs are empty for a run older than 31 days: the lookup reads the history door, which holds 31 days.
  • The fleet says "no run in 14 days" for a repository whose watched branch is not main: unfollow and follow it again with the right branch (the picker follows on main; the watch's branch field can be edited through the world's repository).
  • Following fails outside the console: the picker writes the watchlist through the world gateway, which needs a signed-in session on the same origin.
  • Deeper diagnosis: the realm ships tests/verify.sh, which reconciles every figure here against GitHub's API directly, and scripts/test-views.py.

4. What made this possible

  • Three GitHub endpoints joined as one graph with no ETL, no schedule and no copy: the joins are declared in the realm's types, and the fetch happens per query. A conventional stack mirrors runs into a database on a schedule and answers from the copy.
  • The judgment sits beside the figure: themes() and synthesize() run inside the same query that produced the counts (see the Cypher above), so the prose cannot drift from the table. Conventionally that is a separate pipeline with its own staleness.
  • The same views answer this page, a question typed in words (the ask bar routes a question a view claims to that view, and marks anything the model composed as unverified, Cypher shown), and the world's SQL and OData doors. One definition, validated when saved.
  • There is no backend for this page to deploy or patch: it asks the world by view name at load.
